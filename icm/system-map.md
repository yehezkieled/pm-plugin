# System map: a repository as an edit graph

Adapted from icm-architect's `references/system-map.md` (MIT, © 2026 Jake Van Clief; see [LICENSE](LICENSE)). `/pm:map` follows this. It is optional for an ordinary project and useful once agents should load one part of the code at a time instead of the whole tree.

The map lets a later agent answer "what is this" and "what else moves if I change it" without reading the tree. It is a record library of nouns (object cards), a short shelf of verbs (process cards), and a change-impact index. The source stays the truth; cards cite it and never become a second spec.

| Universe | Meaning |
| --- | --- |
| **live** | In force. Build and cite against these. |
| **leftover** | Still present, no longer the main path. Touch only if that path is in scope. |
| **ghost** | Named or filed but not wired (stubs, dead types, docs of functions that do not exist). Do not build on these. |

Product words and code names often disagree. State both once, in the catalog's Names table ("Board = `docs/pm/items/` read by `read_items`").

## The tree in `docs/pm/map/`

```
docs/pm/map/
├─ AGENTS.md             the map's catalog: names, clusters, where to go (templates/map-AGENTS.md); under 60 lines
├─ CLAUDE.md             the one line @AGENTS.md
├─ CONTEXT.md            the contract for building and refreshing the map (templates/map-CONTEXT.md)
├─ _index.md             generated by `pm.py index` from card frontmatter; never edited by hand
├─ _templates/           object.md and process.md, copied from the plugin; a new card is a copy
├─ objects/<cluster>/    one card per noun, clustered the way an editor asks, not by folder layout
├─ processes/            one card per real movement, only after the nouns exist
└─ effects/CONTEXT.md    if you change X, open these cards
```

The root `AGENTS.md` gets one routing row pointing at `docs/pm/map/AGENTS.md`. The frontmatter of the two templates is the schema: `type`, `status` (stub, verified, stale), `universe` (objects), and for a verified card `verified: YYYY-MM-DD` and `commit:`. Do not create `processes/` or `effects/` empty; three verified clusters beat seven imagined shelves. If one `CONTEXT.md` and a short index would answer "what is X" and "what else moves" (a dozen files), say so and stop there.

## Slices, each stopped for the owner

Stop after each slice unless the owner said to go straight through. A person or a cold walk reads the output before the next slice.

0. **Inventory, no cards.** List the tree: entry points, package and build metadata, configuration, tests, scripts, docs, and an existing `docs/pm/CODEBASE.md` (its facts get absorbed). Infer the nouns (types, tables, modules, durable files) and verbs (movements that repeat), and mark each noun's universe. Present the cluster list and the nouns; get a yes.
1. **Catalog.** Write `AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, copy `_templates/`, and a **stub card for every noun** (frontmatter, title, one sentence). Run `pm.py index`. Add the routing row to the root `AGENTS.md` (show the edit). Walk: "where do I go to understand X?" lands in two hops.
2. **Nouns.** Fill object cards from `_templates/object.md`. Code: cite the type, table, or module as `path:line`; when a comment and the code disagree, the code wins and the card says so. Markdown: cite the file that owns the fact. Mark `status: verified` only with a date, a commit, and citations; `stale` is allowed, a confident wrong date is not. Fill **If you change this** as **Hits** and **Does not hit**, first-order only; "Does not hit" names the obvious next noun that is the wrong one.
3. **Verbs.** Process cards only for movements that actually run. Input, Movement, Output; numbered steps with citations; `consumes` and `produces` as links to object cards; Hits and Does not hit. A small Mermaid flow inside the card is welcome when it shows the movement.
4. **Change impact.** Once there are two or more cards, `effects/CONTEXT.md` is a catalog (with one card, its "If you change this" is the index): "if you are changing X, open these cards". It does not copy the cards' waterfalls; when it and a card disagree, fix the card. Then ask the owner what points into the repository from outside (other repos, CI, scheduled jobs, agent configs) and record each on the card it lands on.
5. **Re-verify** (the map's Verify). Re-read the cited source for every load-bearing claim, especially Hits and Does not hit. Wrong waterfalls cost more than missing cards.

Then `pm.py index`, `pm.py walk`, and the cold walk in [method.md](method.md).

## Absorbing `docs/pm/CODEBASE.md`

The older pm map was one file. Its component and flow diagrams, its table, and its unknowns are input to slice 0: carry every fact still true onto the card or process that owns it, and its `[UNSURE]` edges onto cards as `[UNSURE]` or `ghost`. When every fact has a home, run `pm.py refs docs/pm/CODEBASE.md`, point each referrer at the map, and on the owner's yes `git rm` the old file.

## Refreshing

Re-read the source for the components that changed; update their cards and the date and commit of each one re-verified; set `status: stale` on a card you know is behind but did not re-verify. A `/pm:work` change updates the cards its item touches in the same branch.

## Object card sections

One sentence (product word and code name when they differ) · Why this shape (the load-bearing why) · Shape (keys, constraints, owning files, with citations) · Connected to (owns, owned-by, joins, looks-like-but-is-not) · If you change this (Hits, Does not hit) · Surfaces (who reads or writes it) · See (the source file; at most one other page).

## Walk test for the map

1. Open the root `AGENTS.md`. Is the map one hop away?
2. Open `docs/pm/map/AGENTS.md`. Can you say what the colliding names mean without opening a card?
3. Open one card. Does it cite source, state the why, and give a first-order waterfall?
4. From `effects/CONTEXT.md`, can you name what a stated change hits and what it does not?
5. Follow one See link. Does it land on source, not another essay?
6. Entry, map catalog, and one card stay within about 8,000 tokens (`pm.py walk` reports it).

## Failure modes

Mapping aspiration as live (ghost it) · copying behaviour into cards instead of pointing at the file that owns it · empty process or effects folders · cards marked verified with no citations · reading the whole `objects/` folder in a later session (the catalog exists so you do not) · an effects index that only walks outward, missing what points in from outside.
