# /pm:work

`pm.py` below means `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py"`.

1. Any project work goes through an item: if the request is not on the board yet, add it first with `/pm:plan`'s `add` (the requester's words verbatim), then claim it. With a Git remote, switch to the default branch and fast-forward it from the remote so the board is current. If the user did not name an item, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py" next` and take the first ready item. If none is ready, show the waiting reason and stop.
2. Identify yourself as the current user's name (ask only if it cannot be determined). For a new claim in a repository with a remote, start from the remote default branch. Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py" claim ITEM_ID` with the person's name in a single-quoted heredoc before inspecting or editing product code. Choose a closing marker that does not appear in the name. The CLI fetches the latest default branch, commits the claim there, and pushes without force; only one competing push can land. A rejected push is fetched and checked again. If another person owns it, stop without touching the work. Without a remote, the CLI uses a local file lock.
3. After the claim command succeeds, use `pm/ITEM_ID` as the work branch. If resuming, switch to the existing local branch when present. Otherwise fetch the same remote used by the claim command and switch to `pm/ITEM_ID` from that remote if it exists. If the branch exists nowhere, create it from the claim commit: with a remote, check out the default branch, fetch it, and fast-forward to the shared claim commit first; without a remote, use the current branch where the local claim was saved. For a new claim, create and switch to `pm/ITEM_ID` from the branch containing the saved claim. Do not create a separate branch-only claim commit.
4. Read the item detail, then load only what it touches: for each path in its `touches`, the card or the stage folder's `CONTEXT.md`, then only the inputs that card or contract names (the card's cited source, the contract's Inputs) and the matching rows of `docs/pm/map/effects/CONTEXT.md`. Do not read the rest of the map or the whole tree. With no `touches`, find the relevant code as usual, through `docs/pm/map/AGENTS.md` when a map exists. Keep implementation within the requester's saved intent. Whenever you stop to wait on the owner (a product decision, an approval, missing data), first park the item with `/pm:plan`'s hold command, the question on stdin, so the board shows what is waiting; a question left only in chat or in the notes is lost. When it is answered, resume with `--answer` as `/pm:plan` describes.
5. Make the change, putting every new file where `AGENTS.md` › Where things go says for its kind, by the tie-breakers in `${CLAUDE_PLUGIN_ROOT}/icm/shapes.md`: code writes it, `out/`; a person or an agent writes it for people, `reports/YYYY-MM-DD-<topic>.md`; new raw data goes to its `data/raw/<source>/` with a line in `data/README.md`. No row fits: ask once, recommend a place, and add the row in the same change. Run the project's relevant checks, and update the item's `## Current notes` with a concise summary of current progress (rewrite, do not append a diary). Update the cards the change affects in this same branch (their shape, Hits and Does not hit, date and commit, or `status: stale` if not re-verified) and run `pm.py index` when a card's status changed. File each fact where `${CLAUDE_PLUGIN_ROOT}/docs/placement.md` says it belongs: a decision that shapes future work goes on the card or contract of the part it governs, or into `AGENTS.md` if every session needs it, in this same change; rationale that only explains this change stays in the item notes and PR.
6. Verify before anyone reviews: re-read the item's requester intent and each touched card's Hits and Does not hit (a stage's Outputs and Verify), and check the change against each: it does what the words ask, it handles every Hits entry, and it leaves the Does not hit ones alone. Run `pm.py walk` when the change touched a catalog, a contract, the map, or a workflow skill. Fix what you can; put each mismatch you leave at the top of `## Current notes` with the reason.
7. When the person corrects your output (in chat, in a review comment, or by editing a file you produced), fix it, then record it: `pm.py correct ITEM_ID --kind KIND --where PATH` with what they corrected in a single-quoted heredoc. KIND is a short name such as `missing-tests`; reuse a name the CLI lists when it is the same kind. PATH is the contract, card, or reference file whose instructions produced the output, never the file you edited; leave out `--where` when the person states a project-wide rule or habit (style, tests, wording), so those count together across files. When the CLI says it is the third time, propose the lasting change to that source it names; on a yes, make it on this branch and record it with `--fixed`.
8. When the requested work is complete, commit it on the work branch: every file the change made or edited, including cards and docs, in commits that name the item. Then run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py" finish ITEM_ID` with the completion summary in a single-quoted heredoc. Choose a closing marker that does not appear in the summary. `finish` refuses while any file outside the board is uncommitted and lists them: commit what belongs to the work, remove what does not, and run it again. In a Git repository, it then commits that item's file with its Done state locally on the work branch; the PR merge publishes it to the shared default branch. Do not push separately. Until merge, other clones correctly continue to see the item In flight. Otherwise leave it In flight, still owned by you, and report the next action; when that action is the owner's, hold the item with the question as in step 4.
9. Show `pm.py board` and relate the result to the requester's exact words.

This workflow uses the active Claude Code model. It does not start reviewer agents or switch model providers.

## Reply

Talk in outcomes, not mechanics: plain words, no internal jargon (say "waiting on your decision", not "hold"). The reply must stand alone: lead with the result, then any decision needed. No progress narration. Mark unverified claims `[UNSURE]`. When finished, state what changed for the requester, the branch or PR link, checks run and their real results, what the verify step found, and any decision or review needed. When stopping (owned by someone else, needs a decision), lead with the evidence, then the consequence, then options with a recommendation. Report failures plainly with the command output.
