# /pm:init

Sets up the board and the repository's structure in one pass, following ICM (Interpretable Context Methodology): a small catalog routes to the files that hold the facts, and its `## Where things go` table says where every kind of file goes. Read `${CLAUDE_PLUGIN_ROOT}/icm/shapes.md` before step 3; `${CLAUDE_PLUGIN_ROOT}/icm/method.md` holds the restructure gate (step 5) and the walk test (step 6), so read those sections when you reach them. `pm.py` below means `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py"`. Never replace or rewrite an existing file without the owner's yes, and move nothing before it.

1. Look first: the repository root, `AGENTS.md`, `CLAUDE.md`, `README.md`, any `CONTEXT.md`, `docs/pm/config.json`, `docs/pm/CODEBASE.md`, `docs/pm/map/`, and any `.claude/skills/` or `skills/`. Run `pm.py walk`; it only reads, and shows where the structure fails today.
2. Board: if `docs/pm/config.json` exists, run `pm.py board`, say setup was already present, and go on. Otherwise run `pm.py init`. With a Git remote, run it on the up-to-date default branch; it commits `docs/pm/config.json` and pushes it to the shared default branch.
   Then run `pm.py defaults`. If it says the worker's model or effort is not recorded, ask the owner once which model and effort `/pm:work`'s worker sessions use by default (the model as an exact version such as `claude-sonnet-5-5`, never an alias like `sonnet`, which the CLI refuses; effort: `low`, `medium`, `high`, `xhigh`, or `max`). The validator that checks each worker's work uses the same unless the owner asks otherwise. Ask it together with the yes of step 5 when you ask for one, otherwise in your reply; the rest of setup does not wait for it. Never pick them yourself, and record only the owner's answer, when it comes, with `pm.py defaults --worker-model M --worker-effort E` (add `--validator-model M --validator-effort E` only if the owner set the validator apart). The owner can still name another model or effort for any one item when work starts.
3. Pick the project's shape from `shapes.md` by its repeating unit of work: analysis, automation, skill, app, research, or two of them. Say which and why in one line. Ask only when two shapes fit equally, in one question with your recommendation.
4. `AGENTS.md` is the catalog, from `${CLAUDE_PLUGIN_ROOT}/icm/templates/root-AGENTS.md`: what this is, where things go, where to go for common tasks, and only the rules every session needs (build and test commands, claim an item before changing code or data, keep the requester's words verbatim). Under 60 lines. Its `## Where things go` table gets the spine rows plus the shape's rows from `shapes.md`, one row per kind of thing, never one row per file. Keep a path the project already uses for a kind of thing (an existing `sources/` or `scripts/` stays) and say so; write the real path, not a placeholder. Link `README.md` for the product overview rather than copying it, and never put private or agent-only context in it. `CLAUDE.md` is the one line `@AGENTS.md` when absent; never replace an existing one.
   - `AGENTS.md` absent: write it from the template, filling only facts you checked. Present and already a small catalog: add the `## Where things go` table and the board row if missing, nothing else. Present and carrying content (over 60 lines, or architecture, long procedures, or a glossary): run the restructure gate in `method.md`, finding each section's home in `${CLAUDE_PLUGIN_ROOT}/docs/placement.md`.
   - Architecture and gotchas for one part of the code belong on that part's card in the System map. Offer to build it now with `/pm:map`; it is optional, and worth it when agents will change the code part by part. Until a card exists, that content stays where it is.
5. Put existing files in their places, through the restructure gate in `method.md`. `pm.py walk` lists every file outside the table's places (data at the root, outputs beside their inputs, deliverables kept as notes). For each, propose a move that keeps its file name, or a row when it is a kind the table lacks; run `pm.py refs` for each file that would move, and update the code that reads or writes it in the same change. Add `out/` to `.gitignore`; a generated output already in Git leaves Git as it moves there (`git rm --cached`, then move the file), since the code that writes it rebuilds it. For an analysis, write `data/README.md` with one line per dataset. Show the owner the target tree, the migration map, and the new `AGENTS.md` in full, and ask once for a yes; then `git mv` and re-run whatever the project runs to prove nothing broke. Create no empty folders: a place exists once its first file does. For the skill shape, follow `${CLAUDE_PLUGIN_ROOT}/icm/workflow.md`: ask its questions a few at a time, propose the skill tree (`.claude/skills/<name>/` with numbered stages, each run's files in `runs/<run>/`), and on the owner's yes scaffold it from the templates; `AGENTS.md` routes to the skill's `SKILL.md`.
6. Walk test, both halves, required on every project: run `pm.py walk`, then do the cold walk: answer each cold-walk question in `method.md` from the files alone, opening only what the question allows, and note the file you opened and the answer in one line each. A passing `pm.py walk` is only the first half. Fix the structure until both pass; if a check stays failing, say which and why. After the owner approves the setup and both halves pass, commit the setup changes together as their own commit, including the board, catalog, moves, path edits, and supporting files. Without a Git remote, commit on the current branch. With a remote, create or use a separate setup branch (for example `pm/setup`), commit there, and tell the owner to open a PR; never commit or push setup changes directly to the default branch. Setup is not done, and you must not reply, until the cold walk is answered and the setup commit exists.
7. Show the board and explain `/pm:plan`, `/pm:work`, and `/pm:status` in one line each.

Do not create milestones, epics, sample items, schedules, empty folders, or unrelated docs.

## Reply

Plain words, no jargon ("waiting on your decision", not "hold"); result first, then any decision needed; mark unverified claims `[UNSURE]`. Say whether the board was created or already existed, the recorded worker defaults (or the question asking for them), what was committed or pushed, the project's shape and the structure it now has (a small tree and the `## Where things go` table), what moved or is waiting on the owner's yes, the walk test result (both halves, the cold answers in one line each; a reply without the cold answers is incomplete), and the three commands to use next.
