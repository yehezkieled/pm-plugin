# /pm:init

Sets up the board and the repository's structure in one pass, following ICM (Interpretable Context Methodology): a small catalog routes to the files that hold the facts. Read `${CLAUDE_PLUGIN_ROOT}/icm/method.md` before step 3. `pm.py` below means `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py"`. Never replace or rewrite an existing file without the owner's yes, and move nothing before it.

1. Look first: the repository root, `AGENTS.md`, `CLAUDE.md`, `README.md`, any `CONTEXT.md`, `docs/pm/config.json`, `docs/pm/CODEBASE.md`, `docs/pm/map/`, and any `.claude/skills/` or `skills/`. Run `pm.py walk`; it only reads, and shows where the structure fails today.
2. Board: if `docs/pm/config.json` exists, run `pm.py board`, say setup was already present, and go on. Otherwise run `pm.py init`. With a Git remote, run it on the up-to-date default branch; it commits `docs/pm/config.json` and pushes it to the shared default branch.
3. Decide which kind of project this is, using the signals in `method.md`: an **ordinary project** (an app, library, service, site, or docs) or a **workflow being built** (a repeatable multi-step process Claude will run, to be packaged as a skill). Say what you detected and why. When the signals point to a workflow, or are mixed, confirm it in one question with your recommendation before building anything; when they clearly point to an ordinary project, go on. An ordinary project never gets stage folders.
4. Ordinary project, the light structure only:
   - `AGENTS.md` is the catalog, from `${CLAUDE_PLUGIN_ROOT}/icm/templates/root-AGENTS.md`: what this is, where things live, where to go for common tasks, and only the rules every session needs (build and test commands, claim an item before changing code, keep the requester's words verbatim). Under 60 lines. It links `README.md` for the product overview rather than copying it, and names `/pm:help` for where knowledge goes, without copying the placement table. Never put private or agent-only context in `README.md`. `CLAUDE.md` is the one line `@AGENTS.md` when absent; never replace an existing one.
   - `AGENTS.md` absent: write it from the template, filling only facts you checked. Present and already a small catalog: add the board row if it is missing, nothing else. Present and carrying content (over 60 lines, or architecture, long procedures, or a glossary): run the restructure gate in `method.md`. Classify each section, find its home in `${CLAUDE_PLUGIN_ROOT}/docs/placement.md`, run `pm.py refs` for each file that would move, then show the owner the target tree, the migration map, and the new `AGENTS.md` in full, and ask once for a yes.
   - Architecture and gotchas for one part of the code belong on that part's card in the System map. Offer to build it now with `/pm:map`; it is optional, and worth it when agents will change the code part by part. Until a card exists, that content stays where it is.
5. Workflow being built: follow `${CLAUDE_PLUGIN_ROOT}/icm/workflow.md`. Ask its questions a few at a time, propose the skill tree (`.claude/skills/<name>/` with numbered stages, each run's files in `runs/<run>/`), and on the owner's yes scaffold it from the templates. Existing prompts and notes go through the restructure gate. The root `AGENTS.md`, written as in step 4, routes to the skill's `SKILL.md`.
6. Look for a task system the project already uses: run `pm.py migrate scan` (it only reads). If it finds one (an old pm board, TODO.md, a tasks folder, Beads, GitHub Issues), tell the owner what it found and follow `/pm:migrate` from its plan step: show the plan and counts, and write items only after the owner's yes. Never delete the old system without that confirmation. Do this on a fresh board too; an empty board next to an unmigrated backlog is the wrong outcome.
7. Walk test, both halves: run `pm.py walk`, then answer each cold-walk question in `method.md` from the files alone, opening only what the question allows, and note the file you opened and the answer in one line each. Fix the structure until both pass; if a check stays failing, say which and why. The walk test is not done until the cold half is.
8. Show the board and explain `/pm:plan`, `/pm:work`, and `/pm:status` in one line each.

Do not create milestones, epics, sample items, schedules, empty folders, or unrelated docs.

## Reply

Talk in outcomes, not mechanics: plain words, no internal jargon (say "waiting on your decision", not "hold"). The reply must stand alone: lead with the result, then any decision needed. No progress narration. Mark unverified claims `[UNSURE]`. Say whether the board was created or already existed, what was committed or pushed, which kind of project this is and the structure it now has (a small tree), what moved or is waiting on the owner's yes, the walk test result (both halves, the cold answers in one line each), whether an existing task system was found and where its migration stands, and the three commands to use next.
