pm plugin: one sample project, every command

Follow Dana as they build a tiny link shortener called shortlink and track it with pm. Every command below shows when to use it, the exact invocation, and output captured from a real run in a scratch repo.

The work stays in plain Markdown files, one per item. The board is rendered from them, never stored. Works the same on Haiku, Sonnet or Opus, because each skill just runs a small Python helper.

The same commands also keep the repo easy for an agent to find its way around, using ICM (Interpretable Context Methodology): a small catalog file points to everything, each fact has one home, and a task loads only the files it needs. You never run a second skill for this; icm/ has the method and its credit.

The sample project

Step 1

/pm:init: set up the board and the structure

When to use

Once per repo, before anything else. If a board already exists it just shows it, and it moves or rewrites nothing without your yes.

Say it like this

“set up pm in this repo”, “start tracking work here”, “structure this repo for agents”

You type

The walk test checks whether an agent arriving cold could find its way: is there a small entry file, does every link resolve, does each working folder say what it needs. Here there is nothing to walk yet. Then the board:

Which shape is this project?

Init picks the project's shape by its repeating unit of work, says which in one line, and asks only when two fit equally. Every shape gets the same spine; the shape adds its own rows. The full rows are in the plugin's icm/shapes.md.

ShapeUnit of workAdds to the spine
every project (the spine)docs/pm/items/ tasks, docs/, reports/ for deliverables, out/ for generated files, a clean root
analysisa question answered from datadata/raw/<source>/, data/README.md, src/, notebooks/
automationa runsrc/, config/, .github/workflows/, out/runs/, a runbook
skilla run of a workflow.claude/skills/<name>/ with numbered stages, runs/<run>/
appa change to the codethe source folder, tests/, an optional System map (step 10)
researcha question or a sourcesources/, notes/
Shape: app. shortlink is one Python file and its tests, so it gets the spine plus Source and Tests rows; app.py keeps its name.

shortlink has no AGENTS.md, so init writes one from the plugin's template, filled only with facts it checked, plus a one-line CLAUDE.md that says @AGENTS.md. It never overwrites yours. The catalog points; it does not explain. Its Where things go table is where an agent looks before it creates any file:

# shortlink

A tiny URL shortener: a long URL goes in, a short code comes out. Shape: app. Product overview: [README.md](README.md).

This file routes; the facts live in the files it points at. Where each kind of knowledge goes: `/pm:help`.

## Where things go

Before creating any file, find its kind here and put it in that place. No row fits: ask once, recommend a place, and add the row in the same change. Nothing else goes at the root.

| Kind of thing | Place | Rule |
| --- | --- | --- |
| Tasks: what is being done and what is next | `docs/pm/items/` | `/pm:plan` adds them and `/pm:work` claims them; never made by hand |
| How it works, decisions, gotchas | `docs/` | one file per topic; update it, don't duplicate it |
| Deliverables for people: memos, reports, findings | `reports/` | `YYYY-MM-DD-<topic>.md`; cite the data and the command behind each number |
| Generated outputs | `out/` | written only by code; never hand-edited; gitignored |
| Project files at the root | `README.md`, `AGENTS.md`, `CLAUDE.md`, `.gitignore` | nothing else at the root |
| Source | `app.py` | the whole app, `shorten()`; it keeps its name until it outgrows one file, then moves to `src/` |
| Tests | `tests/` | `test_<part>.py`, run by `python3 -m unittest` |

## Route by task

| If you are | Go to |
| --- | --- |
| adding or tracking work | `/pm:plan` |
| doing any project work (code, data, a deliverable) | `/pm:work`: it adds the item with `/pm:plan` if it is not on the board and hands it to a worker that claims it first |
| asking what is in flight or next | `/pm:status` |

Already tracking work somewhere else? Init also looks for an older system (a pm 0.x board, a TODO.md, a tasks folder) and offers to move it onto the board, see step 13. This sample project has none.

Files in the wrong place (data at the root, a report next to the code) are listed by pm.py walk. Init proposes a move for each, or a new row when it is a kind the table lacks, and moves them with git mv after one yes. A folder the project already uses keeps its name.

Step 2

/pm:plan: add items in the requester's own words

When to use

Whenever someone asks for work. The exact words are saved, not summarised, so nobody later argues about what was asked.

Say it like this

“add a task: …”, “track this”, “queue …”, “remember to …”

You type
/pm:plan Create short links
Let me paste a long URL and get back a short code like /a1b2.
Skill runs (item A; items B, C and D are added the same way)
$ pm.py add <<'PM_END'
Create short links
Let me paste a long URL and get back a short code like /a1b2.
PM_END
Created create-short-links-b153d3: Create short links
Detail: docs/pm/items/create-short-links-b153d3.md
Published to shared origin/main.

Dana adds the other three requests too:

/pm:plan Redirect a short link
Opening /a1b2 should send the visitor to the original URL.

/pm:plan Link expiry
Links should stop working after a while, I don't want old links living forever.

/pm:plan Click counts
Show me how many times each short link was opened.

Each item is a small Markdown file. Notice the wording is exactly what Dana typed, including the “I don't want…”:

---

depends_on: []

# Create short links

## Requester intent
Let me paste a long URL and get back a short code like /a1b2.

## Current notes

Short title on the first line, requester's exact words after it (a lone line counts as both). Nothing is added: no priority, dates or estimates. “Current notes” starts empty and is rewritten as work proceeds (a snapshot, not a diary).

Step 3

Dependencies: /pm:plan again

When to use

Item B is useless until A exists. Say so once and /pm:work will never hand B out early.

Say it like this

“B depends on A”, “don't start redirect until short links are done”

You type
/pm:plan the redirect item depends on create short links, and click counts depends on the redirect
Skill runs
$ pm.py set redirect-a-short-link-9bbffa --depends create-short-links-b153d3
Updated redirect-a-short-link-9bbffa dependencies.
Published to shared origin/main.
$ pm.py set click-counts-790dc4 --depends redirect-a-short-link-9bbffa
Updated click-counts-790dc4 dependencies.
Published to shared origin/main.

A dependency is satisfied only when the item it points to is Done. Comma-separate to depend on several: --depends a-1,b-2.

Step 4

A decision hold: /pm:plan parks the item

When to use

The item needs a human answer before anyone can build it. The hold records the question and takes the item out of “ready”.

Say it like this

“wait on a decision for expiry”, “park link expiry until we decide 404 vs 410”

You type
/pm:plan park link expiry: should expired links show 404 or 410 Gone? Revisit 2026-10-15
Skill runs
$ pm.py hold link-expiry-cc352f --until 2026-10-15 <<'PM_END'
When a link expires, should visitors see a 404 or a 410 Gone page?
PM_END
Parked link-expiry-cc352f: When a link expires, should visitors see a 404 or a 410 Gone page?
Published to shared origin/main.

The date is “when to look again”, not a deadline. A hold keeps any existing claim: if someone owned the item, they still own it while it waits. pm.py resume (step 8) releases it.

Step 6

/pm:work: a worker claims first, then builds

When to use

For any project work, tracked or not yet: a request that is not on the board is added first with your exact words. The session you talk to only coordinates: it hands each item to its own worker session, a full Claude Code session in its own copy of the project that you can open and talk to, which publishes the claim before any code is touched, so two people (or two workers) cannot grab the same item.

Say it like this

“work on create short links”, “start the next task”, “analyse last week's clicks and write it up”

You type
/pm:work            # takes the first ready item
/pm:work create-short-links-b153d3
you ──▶ session (/pm:work) ──▶ worker session: claim ─▶ build ─▶ commit ─▶ validator subagent ─▶ finish
          ▲   files, relays,        │                                         │ findings: fix, re-check (2 rounds)
          │   answers the same      │                                         │
          └──── report ◀────────────┴──── question? item held ◀───────────────┘
Worker runs
$ pm.py claim create-short-links-b153d3 <<'PM_END'
Dana
PM_END
Claimed create-short-links-b153d3 for Dana. Claim is saved before work starts.
Published to shared origin/main.

The claim needs a person's name on stdin. Forget it and you get a clear error, nothing changes:

$ pm.py claim redirect-a-short-link-9bbffa
pm: A person's name is required on stdin.

A second claim of an item already in flight fails, even under the same name, so a ticket never goes to two workers. Only a worker continuing its own claim (after a hold, say) passes --resume:

$ pm.py claim create-short-links-b153d3 <<'PM_END'
Dana
PM_END
pm: create-short-links-b153d3 is already in flight for Dana, so another worker may be on it. Only to continue that same claim, run claim again with --resume.

The worker then creates a branch pm/create-short-links-b153d3 from the claim commit, reads the item and the code it needs (once the repo has a map, only the cards the item touches, step 11), builds it, putting every new file where AGENTS.md says for its kind, runs the project's checks, and rewrites “Current notes”. Before you review, it checks the change against your exact words and lists anything that does not match at the top of the notes. The board now shows the claim:

If someone else owns it, the worker stops and /pm:work tells you who; it will not touch their work. If the push is rejected because someone claimed at the same moment, it re-checks and lets exactly one claim win.

Several items at once. Ask for two ready items that do not depend on each other and the session starts two worker sessions at once, each in its own git worktree under .claude/worktrees/pm-<item>/; pm.py worker list shows what each is doing or waiting on, and your answer to a worker's question goes back into that same session, so it carries on where it stopped. In a terminal each worker is a background session you open with claude attach; in the Claude app the session starts it with the app's own tool and it shows in your session list. The first time, the session asks you which permission setting worker sessions use in this copy (auto is recommended). When an item is Done, its worker's copy is removed and its branch kept. An item that depends on another waits until that one is Done. A single worker works in your checkout, so it sees files you dropped there, and leaves you on its branch when it finishes.

Step 7

Finishing through a PR

When it happens

At the end of a worker's run, when the work is complete and committed on the branch and a separate validator subagent the worker starts, one that did not do the work, has passed it: your exact words, the cards it touches, the Where things go table, and the project's tests. On findings the worker fixes them and asks a fresh validator again, at most twice; if it still fails, or anything waits on you, the item is held with the question and the session asks you.

You do

Push the branch and open a PR as usual. Merging the PR is what tells everyone else the item is Done.

Worker runs: commit the work, have it validated, then finish

finish marks Done only after a passing verdict for the current work. Without a recorded verdict it refuses:

$ pm.py finish create-short-links-b153d3 <<'PM_END'
shorten() returns a 4-character code and stores it; covered by tests/test_shorten.py.
PM_END
pm: create-short-links-b153d3 has no recorded validation. Run the pm:validator agent, then record its verdict with `pm.py validated create-short-links-b153d3 --verdict pass|findings`.
$ git add tests/test_shorten.py && git commit -m "Add shorten() tests (create-short-links-b153d3)"

The worker then starts the validator and waits for its verdict. The validator reads the repository, not the worker's account, and edits nothing. Its verdict has this shape:

VERDICT: pass
Checked:
- intent: a long URL in, a 4-character code like /a1b2 out
- cards: none touched
- places: pm.py places lists nothing; shortlink.py and tests/test_shorten.py sit where the table says
- tests: python3 -m unittest -> 3 tests OK
- committed: git status clean
Findings: none

On VERDICT: findings each finding names a file and line, what is wrong, the rule it breaks, and the fix; in the plugin's own eval, a word_count that split on single spaces came back with its 2 failing tests and a stray notes file at the root. The worker fixes them, commits, and asks a fresh validator, at most two fix rounds. If it still fails, the item waits on you with the findings (Validation still fails after 2 fix rounds: …) instead of going Done.

After each verdict, record the validator's summary against the current commit. The command commits only the item's notes on the work branch:

$ pm.py validated create-short-links-b153d3 --verdict pass <<'PM_END'
python3 -m unittest -> 3 tests OK; new files in their places.
PM_END
Recorded pass validation for create-short-links-b153d3 at f53638671c499bcfe6e9566d2ff4e0a1e15b1739.

Then finish with the completion summary. The CLI keeps the validation record in the final notes. Any later non-board commit makes that pass stale, so fix and validate again before finishing.

$ pm.py finish create-short-links-b153d3 <<'PM_END'
shorten() returns a 4-character code and stores it; covered by tests/test_shorten.py.
PM_END
Finished create-short-links-b153d3 and committed locally.

Step 9 · optional

# Link

A short code and the original URL it stands for; the product says "short link", the code keeps it as a key of `LINKS`.

## Why this shape

One in-memory dict keeps lookup to a single read; nothing is persisted yet, so links vanish on restart.

## Shape

- `LINKS` maps a 4-character hex code to the original URL: `app.py:4`
- Codes come from `secrets.token_hex(2)`, with no check for a code already taken: `app.py:9`

## Connected to

- **owns:** the stored URL
- **owned-by:** nothing; module state
- **joins:** [shorten](../../processes/shorten.md) writes it
- **looks-like-but-is-not:** [Expiry](expiry.md), which is planned, not built

## If you change this

- **Hits:** `shorten()` and `tests/test_shorten.py`, which read `LINKS` directly; the redirect, once built
- **Does not hit:** `README.md`; the board

# Where knowledge goes

Put each fact in the most specific place that owns it, once, and link to it from anywhere else. Anything useful to every contributor lives in the repo, so it travels with the code. The layout follows ICM ([icm/](../icm/README.md)): small routing files point at the files that hold the facts, and an agent loads only what its task needs.

Files that are not knowledge (code, data, notebooks, outputs, deliverables) go where the `## Where things go` table in the root `AGENTS.md` says, by kind; the shapes and tie-breakers behind that table are in [icm/shapes.md](../icm/shapes.md). Findings written for people are deliverables in `reports/`, not item notes and not `docs/`.

| Kind of knowledge | File |
| --- | --- |
| Where things go, where to go for a task, and the few rules every session needs (build and test commands, claim before coding) | `AGENTS.md`, the catalog: under 60 lines; it routes rather than explains. `CLAUDE.md` holds only `@AGENTS.md`. |
| Product overview: what it is, who it is for, goals, how to run it (never private context) | `README.md`. The catalog links to it. |
| What one part of the code is, why it has that shape, what a change to it hits, its gotchas | That part's card in `docs/pm/map/` (`objects/` for things, `processes/` for movements), written by `/pm:map`. Without a map, the doc that already owns that area, linked from the catalog. |
| Which cards to open before a change | `docs/pm/map/effects/CONTEXT.md` |
| Domain vocabulary; product words versus code names | The Names table in `docs/pm/map/AGENTS.md` |
| How a working folder's job is done: inputs, process, outputs, verify, human check | That folder's `CONTEXT.md`. A `CONTEXT.md` is always a folder's contract or router, never a glossary or overview. |
| A workflow being built (the skill shape) | Its skill folder, `.claude/skills/<name>/`: `SKILL.md` routes, `stages/NN_<step>/CONTEXT.md` are the contracts, `_shared/` and `references/` the stable material. Each run's files go in `runs/<run>/`, outside the skill. |
| One task: the requester's exact words, the cards or stages it touches, progress, decisions, corrections | `docs/pm/items/<id>.md`: intent under `## Requester intent`, the owner's answers under `## Decisions`, `touches` and `corrections` in its frontmatter, the rest under `## Current notes`. |
| Where a dataset or source came from, when it arrived, what reads it | `data/README.md` (or `sources/README.md`), one line each |
| Generated lists: the board, the map's card index | Rebuilt by `pm.py board` and `pm.py index`; never edited by hand. |

## Recording decisions

| Stage | What to do |
| --- | --- |
| Question is open | `pm.py hold ITEM_ID` with the question on stdin. The item moves to Waiting and keeps its owner. |
| Answer arrives | Resume with the decider's exact words: `pm.py resume ITEM_ID --answer` with the answer on stdin. They are appended to the item's `## Decisions`, which the worker never rewrites and `finish` keeps, in the same commit as the resume. Do not paraphrase them. |
| Decision shapes future work (a convention, a constraint, a design choice) | Put it on the card or contract of the part it governs, or in `AGENTS.md` if every session needs it, through the normal change for the item. |
| Decision only explains this change | Leave it in the item's notes and in the PR description. |

## Fix the source when a correction repeats

When a person corrects an agent's output, record it with `pm.py correct ITEM_ID --kind KIND --where PATH`. At the third correction of one kind on one source, change that source instead of the next output: the contract, card, or reference file it came from; `AGENTS.md` if it applies to every session; this file if it is about where knowledge goes. Then record `--fixed`.

## Where pm and ICM differed, the rule now

| Question | Rule |
| --- | --- |
| Which entry file is edited | `AGENTS.md`; `CLAUDE.md` is the pointer `@AGENTS.md`. The same pair holds in `docs/pm/map/`. ICM's generated twin files are not used. |
| What `CONTEXT.md` is | A folder's contract or router, as in ICM. pm's old glossary use moves to the Names table. |
| Where architecture goes | The System map's cards, replacing `docs/pm/CODEBASE.md`; `/pm:map` absorbs and retires that file. |
| Where lasting rules go | The card or contract of the part they govern; `AGENTS.md` keeps only what every session needs. |
| Stages | Only for the skill shape, inside its skill folder. Other shapes never get stage folders. |
| The unit of work | A board item. It names the cards or stages it touches; its contract is the requester's words plus those files. |
| Templates | Ship with the plugin in `icm/templates/`; a map keeps copies in `_templates/` so a new card is a copy. |
| Removing files | `git rm` after the owner's yes; git history replaces ICM's `_archive/` folder. |

Before writing anywhere, check the file already covers the fact; update it instead of adding a duplicate. Mark claims you have not verified `[UNSURE]`.

When something looks wrong

  • “A person's name is required on stdin.” The claim needs a name; /pm:work gives its workers your git user name and asks if it cannot find one.
  • “already in flight … another worker may be on it”. A second worker was refused the item. If no worker is on it any more, a worker continues it with claim --resume.
  • “GitHub Issues mirror is off.” Run pm.py mirror github first (mind the publishing warning).
  • An item you finished still shows In flight in another clone. Expected until its PR merges.
  • “is not finished: N files uncommitted”. Commit the work on the branch (or remove what does not belong to it), then finish again.
  • “has no recorded validation”, “has validation findings”, or “changed since validation”. Have a fresh validator check the committed work, record its verdict with pm.py validated ID --verdict pass|findings, and run finish again. After a fix, commit and validate again.
  • “outside the places in AGENTS.md > Where things go”. Move the file to the place for its kind, or add a row for a new kind of thing.
  • “walk test failed”. Each FAIL line names the file and the fix; WARN lines do not fail it. /pm:init and /pm:map fix these themselves.
  • “_index.md is missing or out of date”. A card was added or changed status: run pm.py index.
  • “Fix the source” at the bottom of the board. The same correction came back three times; change the file it names, then record it with --fixed.
  • No Python? Skills fall back to editing the item files by hand, except atomic claiming and GitHub sync.

Install

claude plugin marketplace add /path/to/pm-plugin
claude plugin install pm@pm-plugin

To update later: claude plugin marketplace update pm-plugin, then claude plugin update pm@pm-plugin, and restart Claude Code. The manual covers install, update, and migration in full.

Output in this guide was captured by running the real pm.py in a scratch repository (with a shared remote), except where noted. Item IDs end in a random suffix, so yours will differ.
