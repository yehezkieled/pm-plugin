pm plugin: one sample project, every command

Follow Dana as they build a tiny link shortener called shortlink and track it with pm. Every command below shows when to use it, the exact invocation, and output captured from a real run in a scratch repo.

The work stays in plain Markdown files, one per item. The board is rendered from them, never stored. Works the same on Haiku, Sonnet or Opus, because each skill just runs a small Python helper.

The same commands also keep the repo easy for an agent to find its way around, using ICM (Interpretable Context Methodology): a small catalog file points to everything, each fact has one home, and a task loads only the files it needs. You never run a second skill for this; icm/ has the method and its credit.

Shorthand used below. Skills call a helper script; this page writes pm.py for python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py". You normally never type it yourself: the skills do. The Skill runs blocks show exactly what they run, and the output is real.

The sample project

shortlink: a tiny URL shortener

Dana owns a repo with a README and an app.py stub. There is a shared remote on main. Dana asks for four things:

A Create short links ──▶ B Redirect a short link ──▶ D Click counts
C Link expiry            (parked: "404 or 410 Gone?")

Items move through four states. Only files in docs/pm/items/ hold state; the board is just a view of them.

Step 1

/pm:init: set up the board and the structure

When to use

Once per repo, before anything else. If a board already exists it just shows it, and it moves or rewrites nothing without your yes.

Say it like this

“set up pm in this repo”, “start tracking work here”, “structure this repo for agents”

You type
/pm:init
Skill runs: look first
$ pm.py walk
Walk test: 1 to fix (0 ok, 0 warnings).
FAIL  No entry file: add AGENTS.md as the catalog (where things live, where to go for a task) and CLAUDE.md with the one line `@AGENTS.md`.
These are the mechanical checks. Then walk it cold with the questions in the pm plugin's icm/method.md.
pm: walk test failed: 1 thing to fix.

The walk test checks whether an agent arriving cold could find its way: is there a small entry file, does every link resolve, does each working folder say what it needs. Here there is nothing to walk yet. Then the board:

$ pm.py init
Initialized docs/pm. Add the first item with /pm:plan.
Published to shared origin/main.

Which kind of project is this?

Init says what it sees. When it looks like a workflow, or the signs are mixed, it asks once before building anything; a clear ordinary project goes straight on. The kind decides the structure:

Ordinary projectWorkflow being built
What it isAn app, library, service, site, or docsA repeatable multi-step process Claude will run
StructureA small catalog AGENTS.md; optional System map (step 10)Numbered stages inside a skill folder, each with a contract
Stage foldersNeverstages/01_…, 02_…
Ends asThe productA Claude skill you can package and install
This is an ordinary project (an app with a README and source), so it gets a small catalog and no stage folders.

shortlink has no AGENTS.md, so init writes one from the plugin's template, filled only with facts it checked, plus a one-line CLAUDE.md that says @AGENTS.md. It never overwrites yours. The catalog points; it does not explain:

# shortlink

A tiny URL shortener: a long URL goes in, a short code comes out. Product overview: [README.md](README.md).

This file routes; the facts live in the files it points at. Where each kind of knowledge goes: `/pm:help`.

Step 2

/pm:plan: add items in the requester's own words

When to use

Whenever someone asks for work. The exact words are saved, not summarised, so nobody later argues about what was asked.

Say it like this

“add a task: …”, “track this”, “queue …”, “remember to …”

You type
/pm:plan Create short links
Let me paste a long URL and get back a short code like /a1b2.
Skill runs (item A; items B, C and D are added the same way)
$ pm.py add <<'PM_END'
Create short links
Let me paste a long URL and get back a short code like /a1b2.
PM_END
Created create-short-links-b153d3: Create short links
Detail: docs/pm/items/create-short-links-b153d3-create-short-links.md
Published to shared origin/main.

Dana adds the other three requests too:

/pm:plan Redirect a short link

Step 3

Dependencies: /pm:plan again

When to use

Item B is useless until A exists. Say so once and /pm:work will never hand B out early.

Say it like this

“B depends on A”, “don't start redirect until short links are done”

You type
/pm:plan the redirect item depends on create short links, and click counts depends on the redirect
Skill runs
$ pm.py set redirect-a-short-link-9bbffa --depends create-short-links-b153d3
Updated redirect-a-short-link-9bbffa dependencies.
Published to shared origin/main.
$ pm.py set click-counts-790dc4 --depends redirect-a-short-link-9bbffa
Updated click-counts-790dc4 dependencies.
Published to shared origin/main.

A dependency is satisfied only when the item it points to is Done. Comma-separate to depend on several: --depends a-1,b-2.

Step 4

A decision hold: /pm:plan parks the item

When to use

The item needs a human answer before anyone can build it. The hold records the question and takes the item out of “ready”.

Say it like this

“wait on a decision for expiry”, “park link expiry until we decide 404 vs 410”

You type
/pm:plan park link expiry: should expired links show 404 or 410 Gone? Revisit 2026-10-15
Skill runs
$ pm.py hold link-expiry-cc352f --until 2026-10-15 <<'PM_END'
When a link expires, should visitors see a 404 or a 410 Gone page?
PM_END
Parked link-expiry-cc352f: When a link expires, should visitors see a 404 or a 410 Gone page?
Published to shared origin/main.

The date is “when to look again”, not a deadline. A hold keeps any existing claim: if someone owned the item, they still own it while it waits. pm.py resume (step 8) releases it.

When to use

To start a tracked item. The claim is published before any code is touched, so two people (or two agents) cannot grab the same item.

# Link

A short code and the original URL it stands for; the product says "short link", the code keeps it as a key of `LINKS`.

## Why this shape

One in-memory dict keeps lookup to a single read; nothing is persisted yet, so links vanish on restart.

## Shape

- `LINKS` maps a 4-character hex code to the original URL: `app.py:4`
- Codes come from `secrets.token_hex(2)`, with no check for a code already taken: `app.py:9`

## Connected to

- **owns:** the stored URL
- **owned-by:** nothing; module state
- **joins:** [shorten](../../processes/shorten.md) writes it
- **looks-like-but-is-not:** [Expiry](expiry.md), which is planned, not built

## If you change this

- **Hits:** `shorten()` and `tests/test_shorten.py`, which read `LINKS` directly; the redirect, once built
- **Does not hit:** `README.md`; the board

## Surfaces

| Surface | Role |
| --- | --- |
| `shorten()` | writes |
| tests | read |

Upgrading a project from pm 1.0

pm 1.0 kept architecture in one file, docs/pm/CODEBASE.md. In such a project (captured from a small login service), each session starts with one extra line until it has a map:

This project's architecture is in docs/pm/CODEBASE.md, which this pm version replaces with a System map of cards in docs/pm/map/. Run /pm:map to convert it; nothing is deleted without the owner's yes.

/pm:map moves the old file's facts onto cards. Before retiring it, the skill checks what still points at it:

$ pm.py refs docs/pm/CODEBASE.md
docs/pm/CODEBASE.md
  points at it: AGENTS.md:3 (link), README.md:3 (path)
Outside this repository (other repos, CI, cron, agent configs) nothing is visible from here: ask the owner.

It points both at the map, then removes the old file with git rm once you say yes. For a move, pm.py refs OLD=NEW also refuses a destination whose name differs only in letter case from a file that exists, which would break on macOS and Windows.

# Where knowledge goes

Put each fact in the most specific place that owns it, once, and link to it from anywhere else. Anything useful to every contributor lives in the repo, so it travels with the code. The layout follows ICM ([icm/](../icm/README.md)): small routing files point at the files that hold the facts, and an agent loads only what its task needs.

| Kind of knowledge | File |
| --- | --- |
| Where things live, where to go for a task, and the few rules every session needs (build and test commands, claim before coding) | `AGENTS.md`, the catalog: under 60 lines; it routes rather than explains. `CLAUDE.md` holds only `@AGENTS.md`. |
| Product overview: what it is, who it is for, goals, how to run it (never private context) | `README.md`. The catalog links to it. |
| What one part of the code is, why it has that shape, what a change to it hits, its gotchas | That part's card in `docs/pm/map/` (`objects/` for things, `processes/` for movements), written by `/pm:map`. Without a map, the doc that already owns that area, linked from the catalog. |
| Which cards to open before a change | `docs/pm/map/effects/CONTEXT.md` |
| Domain vocabulary; product words versus code names | The Names table in `docs/pm/map/AGENTS.md` |
| How a working folder's job is done: inputs, process, outputs, verify, human check | That folder's `CONTEXT.md`. A `CONTEXT.md` is always a folder's contract or router, never a glossary or overview. |
| A workflow being built | Its skill folder, `.claude/skills/<name>/`: `SKILL.md` routes, `stages/NN_<step>/CONTEXT.md` are the contracts, `_shared/` and `references/` the stable material. Each run's files go in `runs/<run>/`, outside the skill. |
| One task: the requester's exact words, the cards or stages it touches, progress, decisions, corrections | `docs/pm/items/<id>.md`: intent under `## Requester intent`, `touches` and `corrections` in its frontmatter, the rest under `## Current notes`. |
| Generated lists: the board, the map's card index | Rebuilt by `pm.py board` and `pm.py index`; never edited by hand. |

## Recording decisions

| Stage | What to do |
| --- | --- |
| Question is open | `pm.py hold ITEM_ID` with the question on stdin. The item moves to Waiting and keeps its owner. |
| Answer arrives | Resume with the decider's exact words: `pm.py resume ITEM_ID --answer` with the answer on stdin. They are saved at the top of the item's `## Current notes`, in the same commit as the resume. Do not paraphrase them. |
| Decision shapes future work (a convention, a constraint, a design choice) | Put it on the card or contract of the part it governs, or in `AGENTS.md` if every session needs it, through the normal change for the item. |
| Decision only explains this change | Leave it in the item's notes and in the PR description. |

## Fix the source when a correction repeats

When a person corrects an agent's output, record it with `pm.py correct ITEM_ID --kind KIND --where PATH`. At the third correction of one kind on one source, change that source instead of the next output: the contract, card, or reference file it came from; `AGENTS.md` if it applies to every session; this file if it is about where knowledge goes. Then record `--fixed`.

## Where pm and ICM differed, the rule now

| Question | Rule |
| --- | --- |
| Which entry file is edited | `AGENTS.md`; `CLAUDE.md` is the pointer `@AGENTS.md`. The same pair holds in `docs/pm/map/`. ICM's generated twin files are not used. |
| What `CONTEXT.md` is | A folder's contract or router, as in ICM. pm's old glossary use moves to the Names table. |
| Where architecture goes | The System map's cards, replacing `docs/pm/CODEBASE.md`; `/pm:map` absorbs and retires that file. |
| Where lasting rules go | The card or contract of the part they govern; `AGENTS.md` keeps only what every session needs. |
| Stages | Only for a workflow being built, inside its skill folder. An ordinary project never gets stage folders. |
| The unit of work | A board item. It names the cards or stages it touches; its contract is the requester's words plus those files. |
| Templates | Ship with the plugin in `icm/templates/`; a map keeps copies in `_templates/` so a new card is a copy. |
| Removing files | `git rm` after the owner's yes; git history replaces ICM's `_archive/` folder. |

Before writing anywhere, check the file already covers the fact; update it instead of adding a duplicate. Mark claims you have not verified `[UNSURE]`.

The hooks

  • Session start: prints the board (the same text as step 5), so every session begins knowing what is in flight and ready. It adds one line telling the agent to claim an item with /pm:work before building it and to add work with /pm:plan, so any model follows the board rules. When something looks wrong

  • “A person's name is required on stdin.” The claim needs a name; /pm:work supplies your git user name and asks if it cannot find one.
  • “GitHub Issues mirror is off.” Run pm.py mirror github first (mind the publishing warning).
  • An item you finished still shows In flight in another clone. Expected until its PR merges.
  • “walk test failed”. Each FAIL line names the file and the fix; WARN lines do not fail it. /pm:init and /pm:map fix these themselves.
  • “_index.md is missing or out of date”. A card was added or changed status: run pm.py index.
  • “Fix the source” at the bottom of the board. The same correction came back three times; change the file it names, then record it with --fixed.
  • No Python? Skills fall back to editing the item files by hand, except atomic claiming and GitHub sync.
