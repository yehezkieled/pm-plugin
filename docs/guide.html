pm plugin: one sample project, every command

Follow Dana as they build a tiny link shortener called shortlink and track it with pm. Every command below shows when to use it, the exact invocation, and output captured from a real run in a scratch repo.

The work stays in plain Markdown files, one per item. The board is rendered from them, never stored. Works the same on Haiku, Sonnet or Opus, because each skill just runs a small Python helper.

Which command do I type?

Say what you want in your own words; Claude picks the skill from its description. You can also type the slash command directly.

You want to…CommandDo not use it for
Set up tracking in a repo (once)/pm:initAdding tasks
Add, queue or remember a task; make it wait on another; park it for a decision/pm:plan <request>Doing the task
Start and build a tracked task/pm:work [item-id]Adding new tasks
See who owns what and what is ready next/pm:statusChanging items
Understand how the codebase fits together/pm:map [area]Tracking tasks
Remind yourself what commands exist/pm:helpShowing progress (that is status)

Shorthand used below. Skills call a helper script; this page writes pm.py for python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pm.py". You normally never type it yourself: the skills do. The Skill runs blocks show exactly what they run, and the output is real.

The sample project

shortlink: a tiny URL shortener

Dana owns a repo with a README and an app.py stub. There is a shared remote on main. Dana asks for four things:

A Create short links ──▶ B Redirect a short link ──▶ D Click counts
C Link expiry            (parked: "404 or 410 Gone?")

Items move through four states. Only files in docs/pm/items/ hold state; the board is just a view of them.

Step 1

/pm:init: set up the board

When to use

Once per repo, before anything else. If a board already exists it just shows it and changes nothing.

Say it like this

“set up pm in this repo”, “start tracking work here”

You type
/pm:init
Skill runs
$ pm.py init
Initialized docs/pm. Add the first item with /pm:plan.
Published to shared origin/main.

It also adds a short AGENTS.md pointer (and a one-line CLAUDE.md that says @AGENTS.md) if they are missing, never overwriting yours. The board is empty at first:

$ pm.py board
# Project board

## In flight

- None.

## Queued

- None.

## Waiting

- None.

## Done

- None.

Ready next: none

What was created: only docs/pm/config.json. It was committed and pushed to main so every clone has it.

docs/pm/
├── config.json      ← created now
└── items/           ← one file per item, appears with the first /pm:plan
Step 2

/pm:plan: add items in the requester's own words

When to use

Whenever someone asks for work. The exact words are saved, not summarised, so nobody later argues about what was asked.

Say it like this

“add a task: …”, “track this”, “queue …”, “remember to …”

You type
/pm:plan Create short links
Let me paste a long URL and get back a short code like /a1b2.
Skill runs (item A; items B, C and D are added the same way)
$ pm.py add <<'PM_END'
Create short links
Let me paste a long URL and get back a short code like /a1b2.
PM_END
Created create-short-links-b153d3: Create short links
Detail: docs/pm/items/create-short-links-b153d3-create-short-links.md
Published to shared origin/main.

Dana adds the other three requests too:

/pm:plan Redirect a short link
Opening /a1b2 should send the visitor to the original URL.

/pm:plan Link expiry
Links should stop working after a while, I don't want old links living forever.

/pm:plan Click counts
Show me how many times each short link was opened.

Each item is a small Markdown file. Notice the wording is exactly what Dana typed, including the “I don't want…”:

---
id: "create-short-links-b153d3"
status: "queued"
owner: ""
depends_on: []
hold: ""
hold_until: ""
done_at: ""
intent_length: 61
github_issue: ""
---
# Create short links

## Requester intent
Let me paste a long URL and get back a short code like /a1b2.

## Current notes

Short title on the first line, requester's exact words after it. Nothing is added: no priority, dates or estimates. “Current notes” starts empty and is rewritten as work proceeds (a snapshot, not a diary).

Step 3

Dependencies: /pm:plan again

When to use

Item B is useless until A exists. Say so once and /pm:work will never hand B out early.

Say it like this

“B depends on A”, “don't start redirect until short links are done”

You type
/pm:plan the redirect item depends on create short links, and click counts depends on the redirect
Skill runs
$ pm.py set redirect-a-short-link-9bbffa --depends create-short-links-b153d3
Updated redirect-a-short-link-9bbffa dependencies.
Published to shared origin/main.
$ pm.py set click-counts-790dc4 --depends redirect-a-short-link-9bbffa
Updated click-counts-790dc4 dependencies.
Published to shared origin/main.

A dependency is satisfied only when the item it points to is Done. Comma-separate to depend on several: --depends a-1,b-2.

Step 4

A decision hold: /pm:plan parks the item

When to use

The item needs a human answer before anyone can build it. The hold records the question and takes the item out of “ready”.

Say it like this

“wait on a decision for expiry”, “park link expiry until we decide 404 vs 410”

You type
/pm:plan park link expiry: should expired links show 404 or 410 Gone? Revisit 2026-10-15
Skill runs
$ pm.py hold link-expiry-cc352f --until 2026-10-15 <<'PM_END'
When a link expires, should visitors see a 404 or a 410 Gone page?
PM_END
Parked link-expiry-cc352f: When a link expires, should visitors see a 404 or a 410 Gone page?
Published to shared origin/main.

The date is “when to look again”, not a deadline. A hold keeps any existing claim: if someone owned the item, they still own it while it waits. pm.py resume (step 8) releases it.

Step 5

/pm:status: the board at a glance

When to use

Any time you want to know who owns what, what is stuck, and what to do next. It only reads; it never changes anything.

Say it like this

“status”, “what's next?”, “what is everyone working on?”, “show the board”

You type
/pm:status
Skill runs, and shows

Read it top to bottom: nothing is in flight; B and D are blocked by their dependency; C is Waiting with its question. The single Ready next line answers “what should I do?”. The skill then adds a one-line recommendation, for example: “Start ‘Create short links’: it is the only unblocked item, and it unblocks the redirect. Link expiry needs your decision: 404 or 410?”

This is what /pm:work uses when you do not name an item. It lists queued items with no hold and every dependency done.

Step 6

/pm:work: claim first, then build

When to use

To start a tracked item. The claim is published before any code is touched, so two people (or two agents) cannot grab the same item.

Say it like this

“work on create short links”, “start the next task”, “implement this item”

You type
/pm:work            # takes the first ready item
/pm:work create-short-links-b153d3
Skill runs
$ pm.py claim create-short-links-b153d3 <<'PM_END'
Dana
PM_END
Claimed create-short-links-b153d3 for Dana. Claim is saved before work starts.
Published to shared origin/main.

The claim needs a person's name on stdin. Forget it and you get a clear error, nothing changes:

$ pm.py claim redirect-a-short-link-9bbffa
pm: A person's name is required on stdin.

The skill then creates a branch pm/create-short-links-b153d3 from the claim commit, reads the item and the code, builds it, runs the project's checks, and rewrites “Current notes”. The board now shows the claim:

- [redirect-a-short-link-9bbffa](docs/pm/items/redirect-a-short-link-9bbffa-redirect-a-short-link.md) Redirect a short link — Opening /a1b2 should send the visitor to the original URL.; blocked by create-short-links-b153d3

   main ──●── pm: Claimed …Dana ──●──────────────────▶

If someone else owns it, /pm:work stops and tells you who; it will not touch their work. If the push is rejected because someone claimed at the same moment, it re-checks and lets exactly one claim win.

Step 7

Finishing through a PR

When it happens

At the end of /pm:work, when the requested work is complete and checks pass. If not complete, the item stays In flight, still yours.

You do

Push the branch and open a PR as usual. Merging the PR is what tells everyone else the item is Done.

Skill runs
$ pm.py finish create-short-links-b153d3 <<'PM_END'
shorten() returns a 4-character code and stores it; covered by tests/test_shorten.py.
PM_END
Finished create-short-links-b153d3 and committed locally.

On the work branch the board already says Done:

# Project board

## In flight

- None.

## Queued

- [click-counts-790dc4](docs/pm/items/click-counts-790dc4-click-counts.md) Click counts — Show me how many times each short link was opened.; blocked by redirect-a-short-link-9bbffa

## Waiting

- [link-expiry-cc352f](docs/pm/items/link-expiry-cc352f-link-expiry.md) Link expiry — Links should stop working after a while, I don't want old links living forever.; held: When a link expires, should visitors see a 404 or a 410 Gone page? (review after 2026-10-15)

## Done

- [create-short-links-b153d3](docs/pm/items/create-short-links-b153d3-create-short-links.md) Create short links — shorten() returns a 4-character code and stores it; covered by tests/test_shorten.py.

Ready next: redirect-a-short-link-9bbffa Redirect a short link
You (or the skill) then run
git push -u origin pm/create-short-links-b153d3
gh pr create --fill

Why not Done everywhere immediately? finish commits only that item's file, and only on the work branch. Until the PR merges, other clones correctly see it In flight under Dana. After the merge it is Done for everybody, with no board file to conflict on. (This sample used a local merge in place of a hosted PR; the result is the same.)

work branch:  claim ─▶ code ─▶ notes ─▶ finish (Done, local)
                                            │  PR opened
main:                                       └─ merge ─▶ Done for everyone

Step 9 · optional

GitHub Issues mirror: pm.py mirror and pm.py sync

When to use

Only if teammates who never open the repo want to follow along in GitHub Issues. Off by default. The local files stay the source of truth; issues are a one-way copy.

Say it like this

“mirror the board to GitHub issues”, “sync the board”

Publishing warning. Turning this on authorizes copying each item's requester intent and current notes to this repository's GitHub Issues audience. The command prints that disclosure. There is no slash command for it: ask Claude, or run the CLI.

Check the setting, and see sync refuse while it is off

GitHub Issues mirror: off
$ pm.py sync

Step 10

/pm:map: explain the codebase with diagrams

When to use

You are new to a codebase, or want an architecture and data-flow overview. It does not touch the board. Add an area to zoom in.

Say it like this

“how does this codebase work?”, “map the code”, “give me an architecture overview”

You type
/pm:map
/pm:map redirects

The skill reads entry points, config, tests and docs, then writes docs/pm/CODEBASE.md (Mermaid component and flow diagrams, a components table, entry points, and anything unverified marked [UNSURE]). In the chat it draws the same diagrams in ASCII so they read in a terminal. This one is written by the model, not the helper script, so the wording varies from run to run. For shortlink at the end of step 1, a reply looks like this:

shortlink is a single-file Python app: app.py will turn long URLs into short codes.
Only the shorten() stub exists so far. [UNSURE] where codes will be stored: nothing is persisted yet.

 caller ──▶ shorten(url)  (app.py:2) ──▶ short code   (stub, returns nothing yet)

Written to docs/pm/CODEBASE.md

As the project grows, the diagrams grow with it: components and their dependencies, then input → logic → stored/returned output, each with source paths next to the nodes.

Step 11

/pm:help and the two hooks

/pm:help: when to use

You forgot the commands. It prints this card and stops. Say “how do I use pm?” or “what commands are there?”.

Hooks: automatic

Nothing to type. They are on once the plugin is installed and never block your session.

You type
/pm:help
/pm:init             Set up docs/pm and concise AGENTS.md guidance
/pm:plan <request>   Record a request verbatim as a queued item
/pm:work [item-id]   Claim first, then implement and update notes
/pm:status           Show owners, waiting items, and what's ready
/pm:map [area]       Write a codebase overview with diagrams
/pm:help             Show this guide

The hooks

  • Session start: prints the board (the same text as step 5), so every session begins knowing what is in flight and ready.
  • Stop: if you changed code but no item file, it reminds the agent once: “Code changed without an item detail update. If this work is tracked, rewrite its Current notes and refresh affected project docs before finishing.”

When something looks wrong

  • “A person's name is required on stdin.” The claim needs a name; /pm:work supplies your git user name and asks if it cannot find one.
  • “GitHub Issues mirror is off.” Run pm.py mirror github first (mind the publishing warning).
  • An item you finished still shows In flight in another clone. Expected until its PR merges.
  • No Python? Skills fall back to editing the item files by hand, except atomic claiming and GitHub sync.
