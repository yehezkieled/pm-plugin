Design · revision 6 · built, installed, verified across four models; ships with the plugin as docs/blueprint.html

pm-plugin Blueprint

A project system in plain markdown with four levels: milestone → epic → ticket → subtask. One file per thing, seven slash skills, three hooks, and a GitHub mirror, so you and your agents work from the same board in any repo.

How /pm:work picks a ticket

The picker reads every ticket's depends_on, the same data the epic's Flow section is drawn from. A ticket is ready when it is todo, every ticket it depends on is done, and nobody owns it. Among ready tickets it takes the highest priority, then the earliest in the flow. The claim is committed before the branch is made, so two agents starting at the same time never take the same ticket. The board shows "blocked by T011" on a card that is waiting.

/pm:work, one ticket per run

claim → plan (always) → approval if required → branch → subtasks by TDD → four gates → PR or merge → done

/pm:plan, /pm:status, /pm:retro, hooks

/pm:plan

The only skill that creates or restructures. Sub-commands: milestone, epic, ticket, bug, idea, apply. With no argument it reviews the current milestone with you: what is missing, what should move, and breaks epics into tickets. Ends with a sync.

/pm:status

Prints the board for the current milestone, then three paragraphs: where we are, what is blocked, what is next. Never a date or a countdown. Optionally posts the paragraphs on the milestone.

/pm:retro (milestone close)

What shipped, what moved to the next milestone, which gates caught bugs, what was re-planned. Lessons become proposed edits to CLAUDE.md or decisions.md. Closes the milestone on GitHub. Nothing written until you approve.

hooks

SessionStart: if docs/pm exists, print the board line and the skill map. PreToolUse (plan gate): on a ticket branch, an Edit, Write or Bash call that would change code is refused until the ticket's ## Plan is written and, for plan: required, approved; while a Bug: ticket says tests: frozen, test files are refused too; a ticket claimed by a routine can never be merged or unfrozen by it. Docs and markdown are always allowed. Stop: if source files changed but no ticket file did, print a one-line warning. The stop hook never blocks.

Where plan mode and grilling sit

Two habits raise quality more than anything else in the loop: a questioning round (a grilling session) before anything is written, and a read-only plan before anything is edited. The questioning style borrows the essence of Matt Pocock's grill-me skill, credited in the plugin README and built in rather than installed. Both habits live inside the SKILL.md files themselves: the instructions say when to ask, one question at a time, and the frontmatter pins which tools the skill may use. The routine variant removes the question tool so an unattended run can never stall.

Cost: one round of questions per epic or ticket, and one approval per flagged ticket. In return, acceptance is testable, design choices are yours, and the routines stay safe: an unattended run only takes tickets whose plan is none or already approved.

Routines, per project

The plugin ships the skills; the timer is the project's own. Each project decides whether a routine runs, how often, and how much it may take. Turning one on is a pm block edit plus one cron entry; turning it off is the same edit. Two routines are designed:

Work routine

Runs /pm:work --routine. Takes only tickets marked auto: yes whose plan is none or approved, at most auto_cap per run, always on a branch with a PR, never merges, stops at the first failing gate and leaves the ticket in progress with a note. You review the PRs when you like.

Audit routine

Runs /pm:audit. Files tickets, never code. Each ticket carries the evidence: file and line, the test that would catch it, or the decision it contradicts. Capped per run. Tickets it files are auto: no until you flip them, so the audit cannot feed the work routine without you.

Caution built in: an unattended audit can drown you in small tickets. The cap and the evidence rule keep it honest, and every audit ticket stays auto: no until you flip it.

you, once per project:   edit pm block  →  routines: work=on audit=on, auto_cap: 2
                         put two commands on a timer (cron, or a CI job), e.g. nightly /pm:audit, hourly /pm:work --routine

each run:                /pm:audit  →  new tickets, auto: no  →  you flip some to auto: yes
                         /pm:work --routine  →  picks by the Flow, opens PRs  →  you merge

What the failures changed

Before the fixes, Haiku merged in routine mode, built a plan: required ticket without approval, merged under merge: ask, skipped the fork backup, and sent "apply the proposals" to the status skill. Opus started a ticket whose dependency was still open because the prompt said "no questions". Prose rules did not hold for the weaker or bolder models, so the rules became mechanical, each with unit tests:

  • pm.py claim refuses a ticket with an open dependency (only --force overrides), prints the exact commit, push and branch commands for the project's flow, and warns when plan approval is needed.
  • pm.py next --routine names the routine owner, and the plan gate refuses git merge and gh pr merge on a ticket owned by a routine.
  • The plan gate blocks any code edit on a ticket branch until the plan is in the ticket and, for plan: required, approved.
  • pm.py backup does the fork copy, so the status skill runs a command instead of remembering a rule.
  • Skill text: "do not ask me questions" is not an approval and not a merge decision; one question per call in interviews; the status skill hands "apply the proposals" to the plan skill.

Also observed, not a failure: when asked directly to add a function, none of the four models went through a ticket; the stop hook printed its reminder every time. That is the designed behaviour, the reminder is the nudge.

9 · Decisions the build settled

  • Skill names: /pm:init, /pm:brainstorm, /pm:plan, /pm:work, /pm:status, /pm:retro, /pm:audit, /pm:help. Plugin name pm; Claude Code adds the pm: prefix itself, the folders are skills/init and so on. Typing /pm lists them.
  • Docs live under docs/pm/ so they never collide with a repo's own docs folder.
  • Decisions are one file, docs/pm/decisions.md, newest entry first. Say "drop it" and it goes.
  • Ticket status has four values: todo, in progress, review, done. "review" means a PR is open. Blocked is not a status; it is a dependency that is not done, and the board shows it as a note on the card.
  • GitHub mapping: milestone → milestone, epic → issue labelled epic with a task list of its tickets, ticket → issue, PR closes the ticket issue. Sync is one-way; edits made on GitHub are overwritten.
  • No time tracking of any kind. No target dates, no deadlines, no hour or day estimates, no velocity, no "on track / late". Milestones are versions in order. If a status report ever needs a "when", the answer is "when the tickets are done". Enforced three ways: the templates have no such fields, every SKILL.md carries the rule in words so the agent never asks for or prints one, and tests/test_no_time_tracking.py fails if any of those files mention them.
  • Routines are opt-in per project through the pm block. The plugin never schedules anything by itself. Routine runs only take auto: yes tickets whose plan is none or approved, and never merge. An unattended run never makes a design choice.
  • Merging a PR is ask by default; auto is a per-project choice.
  • Claiming commits owner: on main, or pushes when a remote exists, before branching. A claim whose branch has no commits and whose owner session is no longer running can be taken over, with a note.
  • Old planning docs in an existing repo are moved to docs/archive/ when you adopt the plugin there, not deleted, and only after you say yes.
  • Scripts are Python 3.12 with no third-party packages, plus small bash. No Python on a machine is fine: the SKILL.md rules let the agent do the same edits by hand, and doctor.sh says what to install.
  • Wording: plain words everywhere, and the two words you banned never appear.
  • Plan step is part of /pm:work for every ticket. A plan: required ticket in an interactive session switches the session into plan mode itself: read-only until you approve the plan at the exit, then the approved plan is copied into the ticket. Routine and headless runs have nobody to approve, so they skip such tickets; if a plan-mode tool is missing the skill writes the plan into the ticket and asks, or stops, before any edit.
  • Scripts and the pm block: one command line entry point pm.py; the pm block is plain key: value lines, one per line, because the scripts parse it. Values like mirror: yes are accepted and read as on.
  • Review by fresh eyes. The review gate starts two read-only subagents at once, pm:verifier (check command, every acceptance line against the diff, widened scope) and pm:reviewer (bugs, edge cases, error handling, security, hollow tests). Sonnet by default, review_model in the pm block overrides. A normal run fixes their findings; a routine run stops at them, notes them in the ticket and the PR, and files out-of-scope ones as tickets.
  • Questions at the plan step, per ticket. In an interactive session every ticket asks what it leaves open, at most three questions, shows the plan and asks to go ahead before the first edit, and asks which model reviews it, Sonnet preselected or Opus. A ticket approved in plan mode skips the go-ahead. Routine and headless runs skip the questions and take the defaults.
  • Bug fixes freeze their tests. On a Bug: ticket the reproducing test is committed, then pm.py freeze; from there the gate refuses edits to test files. A test that is wrong needs a person: pm.py unfreeze --reason records why under Notes. This ticket's own test stays in the same ticket, an unrelated wrong test becomes a new ticket. Routines never unfreeze.
  • Dismissed, with a reason. A fifth status for findings nobody wants: pm.py dismiss --reason. Out of the counts and the ready list, the file kept, the issue closed as not planned, and validate flags any ticket that still depends on it. Audit tickets carry confidence: high | medium | low.
  • The plan follows the build. When the build departs from the ticket's plan, the docs gate rewrites Approach and Touches to what was done and says why under Notes.
  • Lessons reach CLAUDE.md. The retro offers up to three one-line rules for CLAUDE.md, written only after a yes.
  • Routines have a recipe. Two templates, a crontab and a GitHub Actions job, so a project copies instead of writing.
  • Evals ship with the plugin. The scenario runners and their checks live in evals/; results are ignored by git. Run them after changing a skill, hook, or agent, and when a new model appears.
